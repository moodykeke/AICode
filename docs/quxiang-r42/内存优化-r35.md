# r35：深入内存体检 + 纸纹优化（含全量记账工具）

## 一、先说体检方法（这次是"点名"而不是估算）

app 里画布大部分是**离屏**的，`window.__mem`（只数挂在 DOM 上的）看不到它们。
这次用两层手段把内存点名到归属：

1. **CDP `Runtime.queryObjects(HTMLCanvasElement.prototype)`** —— 枚举进程里所有画布对象（含离屏、
   含各处缓存），逐个算 `w × h × 4`；每步之前先 `HeapProfiler.collectGarbage` 只统计"活着"的，
   避免把待回收的垃圾当成占用。
2. **新增 `开发与验证/mem-tag.js`**：给已知归属的画布打 `__tag`（stage / paper / photo-crop /
   photo-frame-* / card-front / card-back …），审计输出就能按归属点名；未标记的大画布一眼可见。

## 二、体检发现（1440×838 舞台，DPR 1）

| 状态 | 总占用 | 主要持有者 |
| --- | --- | --- |
| 空载 | **9.5MB** | stage 4.6 + **paper 4.6** + 卡片正反面 0.34 |
| 合影后 | **15.6MB** | 多了 **第二张 paper（4.6MB，且关掉暗房也不消失）** + 抓帧裁切 1.4 |
| 班级人像 52 张 | +11.1MB（另一处记账） | 每张 200×280×4 ≈ 224KB，正对应舞台 ~100px 卡在 retina 下所需 |

两个真问题：**纸纹与舞台同尺寸常驻**（DPR2 桌面上是 19MB）；**拍照提分辨率时 `rebuildPaper()`
新建一张纸纹、旧的被 pattern 引用着不释放**（4.6MB 泄漏，DPR2 是 19MB）。

## 三、优化（质量不变的前提下）

1. **纸纹降分辨率**：主纸纹按 **120 万像素预算**生成（`rebuildPaper` 内），绘制时按原尺寸放大。
   纸纹是"渐变 + 细小颗粒"的软纹理，且颗粒尺寸随画布尺寸一起缩放 —— 放大后**颗粒的视觉大小不变**，
   只是略微变软。实测纸纹 4.6MB → **2.66MB**（DPR2 桌面 19MB → 2.66MB）。
2. **主动释放上一张纸纹**：`rebuildPaper()` 里把旧画布显式清成 1×1（不能只靠 GC —— 旧的
   `CanvasPattern` 还引用着它的源画布）。审计里能看到旧的那张变成 `1×1`，不再占内存。
3. **`paperFill()` 的图案按同一比例放大**：纸色遮挡（角色底部的"纸面阴影"）必须与纸面**逐像素对齐**，
   否则会露出图案拼缝。这条不改视觉效果，只保证对齐。

**踩坑记录**：第一次我把"复用同一张画布"塞进了 `makePaperCanvas` —— 结果**所有调用者共用一张**：
`makePaperCanvas(8,8)` 之类的纹理调用把主纸纹改成了 110×110。改成只在 `rebuildPaper`（主纸纹）
这一处做降分辨率与释放，其它纹理调用保持各自新建。

## 四、效果（同一状态实测）

| | 优化前 | 优化后 |
| --- | --- | --- |
| 空载总占用（DPR1 桌面） | 9.5MB | **7.6MB（−20%）** |
| 纸纹（DPR1 / DPR2 桌面） | 4.6 / 19MB | **2.66 / 2.66MB（−42% / −86%）** |
| 合影并关掉暗房后 | 15.6MB | **9.0MB（−42%）**，且旧纸纹归 1×1 |
| 渲染质量 | — | 截屏核对：纸面颗粒与遮挡底影一致，无拼缝 ✓ |

## 五、后续可做（未动，风险与收益都写清）

- 班级卡 11.1MB：可只烤人像、相框与名牌改为每帧矢量绘制（省 ~0.7MB，字更锐），或把卡按 1.5× 烤（省 ~3MB，轻微变软）；
- 合影抓帧 1.4MB 常驻（按 `'` 可重开的设计保留）；如需更省可在关掉暗房后延迟释放。
